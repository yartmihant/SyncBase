# SyncBase

SyncBase — консольный инструмент для безопасной двусторонней синхронизации
локального вольта с папкой приложения на Яндекс.Диске.

Вольт — папка с файлом `.syncbase`. Её непосредственные подпапки считаются
проектами и зеркалируются как `app:/<project>/`. Промежуточного уровня категорий
больше нет. Для независимых наборов проектов можно создать несколько вольтов с
отдельными OAuth-приложениями и токенами.

## Установка

```bash
pip install syncbase
```

Для разработки:

```bash
pip install -e .
```

Из исходного каталога также работает совместимый launcher:

```bash
python sync_base.py list
```

## Настройка Яндекс.Диска

1. Зарегистрируйте приложение на [Яндекс.OAuth](https://oauth.yandex.ru/). При создании выбери тип «Для доступа к API»
2. Выдайте приложению право `cloud_api:disk.app_folder`.
3. Получите OAuth-токен. Для этого перейдите на https://oauth.yandex.ru/authorize?response_type=token&client_id=<CLIENT_ID>
4. Создайте локальную папку вольта и файл `.syncbase`:

```bash
cd /путь/до/вольта
echo 'YANDEX_DISK_TOKEN=y0__xCPz...' > .syncbase
```

Файл `.syncbase` содержит секрет. Не добавляйте его в Git. SyncBase всегда
исключает `.syncbase` и `.sync_cache` из синхронизации независимо от правил
`.syncignore`.

Каждый токен с доступом `cloud_api:disk.app_folder` видит только папку своего
OAuth-приложения. Перед первым сохранением проверьте корень командой
`syncbase list`.

## Команды

```bash
# Показать локальные и облачные проекты вольта
syncbase list

# Обработать все проекты вольта
syncbase status all
syncbase save all
syncbase load all

# Обработать явно указанный проект
syncbase status MyProject
syncbase save MyProject
syncbase load MyProject

# Из MyProject/ или любой вложенной папки — обработать текущий проект
syncbase status
syncbase save
syncbase load
```

Команды можно запускать из корня вольта или любой вложенной папки: SyncBase
ищет ближайший `.syncbase`, поднимаясь вверх по дереву каталогов.

## Защита от потери данных

SyncBase блокирует операцию, если она:

- перезапишет более новый файл более старым;
- удалит файл, существующий только на целевой стороне.

Для осознанной принудительной синхронизации добавьте `-f` или `--force`:

```bash
syncbase save --force
syncbase load all --force
```

## `.syncignore`

Файл `<vault>/.syncignore` исключает проекты при массовых командах. Файл
`<vault>/<project>/.syncignore` задаёт правила для содержимого конкретного
проекта. Поддерживаются шаблоны `*`, `?`, исключения `!` и комментарии `#`.

```gitignore
.git/
__pycache__/
*.log
node_modules/
!important.log
```

Если проектный `.syncignore` отсутствует, SyncBase при первом сканировании копирует
в него встроенный `src/syncbase/.syncignore.example`, поставляемый с пакетом.
Шаблон исключает каталоги Git/Mercurial/SVN, виртуальные окружения и кэши Python,
`node_modules` и кэши JS-сборщиков, `.idea`, `.vscode`, служебные файлы ОС и
временные файлы редакторов. Простые имена, например `__pycache__/` и `.DS_Store`,
действуют на любой глубине; начальный `/` привязывает точное правило к корню.
Общие имена `build`, `dist`, `data`, файлы `.env` и произвольные `*.tmp` не
исключаются шаблоном: в вольте они могут содержать нужные пользователю данные.

Существующий `.syncignore`, включая пустой, сохраняется без изменений.
Обновление библиотеки не дописывает правила в ранее созданные проекты;
их правила можно изменить вручную. Проектный `.syncignore` синхронизируется вместе с проектом;
корневой файл остаётся локальной настройкой вольта.

## Структура вольта

```text
MyVault/
├── .syncbase       # локальный OAuth-токен, никогда не синхронизируется
├── .syncignore     # правила выбора проектов для массовых команд
├── ProjectA/
│   ├── .syncignore # правила содержимого проекта
│   ├── .sync_cache # локальный кэш status, не синхронизируется
│   └── ...
└── ProjectB/
    └── ...
```

Облачный корень содержит проекты без дополнительного уровня категории:
`app:/ProjectA/`, `app:/ProjectB/` и так далее.

## Python API

```python
from syncbase import SyncVault, find_vault

vault_path, token = find_vault() or (None, None)
if vault_path and token:
    SyncVault(vault_path, token).run_all("save")
```

## Индексация и кэш

Команды остаются прежними. Начиная с 0.2.2, `.sync_cache` хранит два независимых
набора данных: снимок последнего `save`/`load` для `status` и индекс локальных
MD5 для ускорения сканирования. Повторный `status` обновляет индекс, но продолжает
показывать несохранённые изменения относительно прежнего снимка.

При каждом проходе проверяются имена и метаданные всех включённых файлов.
Содержимое читается только для новых файлов или при изменении размера,
`mtime_ns`, `ctime_ns`, идентификатора файловой системы или файла (`dev`, `ino`).
После `load` неизменившиеся файлы не хешируются повторно. Первый проход, миграция
старого кэша и изменение большинства файлов всё ещё требуют чтения содержимого.

Кэш версии 2.0 читается автоматически: следующий `save`, `load` или `status`
строит индекс и записывает версию 3.0. Формат — компактный JSON с секциями
`project_info`, `files`, `dirs`, `statistics` и `local_index`. Последняя секция
содержит MD5 и подпись `[size, mtime_ns, ctime_ns, dev, ino]` по относительному пути.
Запись выполняется через временный файл и атомарную замену. `.sync_cache` и
`.sync_cache.*.tmp` никогда не отправляются в облако. Повреждённый индекс
перестраивается; при потере всего кэша снимок для `status` создаётся новым `save`/`load`.

Повторное использование MD5 опирается на метаданные файловой системы. Изменение
содержимого с сохранением **всех** полей подписи не обнаруживается без полного
чтения; в Windows `ctime` означает время создания, а не последнего изменения.
Если сторонняя программа сохраняет исходные метаданные при редактировании,
удалите `.sync_cache` перед следующим запуском `save`/`load`, чтобы пересчитать
все хеши. Это также удалит прежний снимок для `status`.

Облачные метаданные при `save`/`load` запрашиваются заново. Обход использует один
пул из максимум 16 потоков: дочерние каталоги поступают в очередь сразу после
получения родительского списка. Продолжительность зависит от количества папок,
задержек API и ограничений Яндекс.Диска; локальный кэш не устраняет эти запросы.

Для замера локальной индексации без сети и токена:

```bash
python work/benchmark_indexing.py --files 2000 --kib 128
```

Скрипт создаёт временный проект, измеряет первый проход, повторный проход и
проход после изменения 10 файлов, включая запись кэша. В контрольном замере на
Windows (2 000 файлов, 250 МиБ) повторный проход сократился с 0,527 до 0,072 с,
а проход с 10 изменёнными файлами — с 0,560 до 0,122 с. Это локальные измерения
с прогретым файловым кэшем ОС, без передачи данных и облачного сканирования.
